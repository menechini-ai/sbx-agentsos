Arquitetura de Agentes
1. Objetivo

Construir uma arquitetura local e modular para agentes de IA na qual:

cada agente tenha uma identidade e responsabilidade claramente definidas;
agentes possam possuir suas próprias skills;
skills sejam reutilizáveis;
a memória seja persistente entre sessões;
diferentes agentes possam compartilhar conhecimento;
sessões possam ser retomadas posteriormente;
decisões e aprendizados sejam preservados;
o conhecimento seja versionável;
Claude Code, Codex e outros runtimes possam trabalhar sobre a mesma estrutura;
a memória não dependa exclusivamente do contexto da conversa.

A arquitetura será inspirada no conceito de agentes baseados em arquivos Markdown e utilizará o ai-memory como infraestrutura de memória persistente.

2. Princípios

A arquitetura seguirá cinco princípios fundamentais.

2.1. O agente é definido por contexto + regras + skills + memória

Um agente não será representado apenas por um prompt.

Ele será composto por:

Agente
├── Identidade
├── Regras
├── Contexto
├── Skills
├── Memória
└── Histórico de trabalho

2.2. AGENTS.md é o contrato do agente

Cada agente terá um AGENTS.md.

Esse arquivo deverá conter somente aquilo que precisa estar disponível permanentemente ao agente:

quem ele é;
qual é sua missão;
quais são suas responsabilidades;
quais são suas restrições;
como deve tomar decisões;
onde encontrar suas skills;
onde encontrar informações adicionais;
como utilizar a memória.

Informações grandes ou específicas não devem ser colocadas diretamente no AGENTS.md.

O arquivo deve funcionar como um roteador de contexto.

Exemplo:

Para regras de desenvolvimento:
→ consultar skills/development/

Para memória:
→ consultar ai-memory

Para decisões arquiteturais:
→ consultar memória do projeto

Para handoff:
→ utilizar a skill de session-handoff

4. Separação entre Agent OS e Memory Engine

O projeto será dividido conceitualmente em duas camadas.

┌───────────────────────────────────────┐
│              Agent OS                 │
│                                       │
│  Agents                               │
│  Skills                               │
│  Rules                                │
│  Workflows                            │
│  Project structure                    │
│                                       │
└───────────────────┬───────────────────┘
                    │
                    ▼
┌───────────────────────────────────────┐
│             ai-memory                 │
│                                       │
│  Persistent memory                    │
│  Session continuity                   │
│  Handoffs                             │
│  Retrieval                            │
│  Knowledge compilation                │
│  Search                               │
│                                       │
└───────────────────────────────────────┘


O Agent OS define como os agentes trabalham.

O ai-memory define como o conhecimento persistente é armazenado e recuperado.

Essa separação é importante para que a arquitetura não fique acoplada ao mecanismo de memória.

5. ai-memory

O ai-memory será utilizado como mecanismo oficial de memória.

Ele mantém uma wiki de Markdown como fonte de verdade e utiliza SQLite como índice derivado para recuperação, busca textual e outras formas de retrieval.

memory/

6. Localização da memória

A memória deverá ficar isolada da definição dos agentes.

Conceitualmente:

agent-os/
│
├── agents/
│
├── skills/
│
├── docs/
│
└── memory/
    └── ai-memory/


Entretanto, o diretório físico utilizado pelo ai-memory deverá seguir a configuração oficial da ferramenta.

O projeto atualmente organiza sua memória em uma estrutura semelhante a:

<data_dir>/
├── wiki/
├── raw/
├── db/
├── models/
└── logs/


onde wiki/ contém o Markdown considerado fonte de verdade e db/ contém o índice SQLite derivado. 
G
GitHub

Portanto, não devemos modificar arbitrariamente a estrutura interna do ai-memory.

7. Memória como conhecimento, não como configuração

Uma distinção importante:

AGENTS.md
    ↓
REGRAS DO AGENTE

ai-memory
    ↓
CONHECIMENTO ADQUIRIDO


Por exemplo:

Regra
Sempre executar testes antes de abrir um PR.


Isso é uma regra permanente do projeto e pertence ao AGENTS.md.

Conhecimento
O serviço X apresenta timeout quando recebe mais de 500
requisições simultâneas.


Isso é conhecimento adquirido e pertence à memória.

Essa separação evita transformar a memória em um enorme arquivo de instruções.

O próprio ai-memory recomenda que regras duráveis do projeto permaneçam no arquivo de instruções do agente, enquanto fatos, decisões e aprendizados podem ser armazenados na wiki.

9. Hierarquia de agentes

O sistema poderá possuir um agente principal responsável por delegar tarefas.

                    CEO
                     │
          ┌──────────┼──────────┐
          │          │          │
          ▼          ▼          ▼
      Researcher  Developer  Marketing
          │          │          │
          ▼          ▼          ▼
       Research    Coding     Content
        Skills     Skills      Skills


O CEO não precisa executar todas as tarefas.

Sua função principal será:

entender objetivo
       ↓
planejar
       ↓
delegar
       ↓
avaliar resultado
       ↓

10. Skills

Skills representam capacidades operacionais.

Cada skill deverá ser autocontida.

Exemplo:

skills/
├── research/
│   ├── SKILL.md
│   └── references/
│
├── coding/
│   ├── SKILL.md
│   └── references/
│
└── session-handoff/
    └── SKILL.md


Uma skill deve responder:

Quando deve ser utilizada?
Quando não deve ser utilizada?
Qual é o procedimento?
Quais ferramentas podem ser utilizadas?
Qual é o resultado esperado?
Onde os artefatos devem ser armazenados?
11. Skills globais vs skills do agente

Existirão dois níveis.

Skills globais

Disponíveis para diversos agentes:

skills/
├── research/
├── documentation/
└── session-handoff/

Skills específicas

Disponíveis somente para determinado agente:

agents/
└── developer/
    └── skills/
        ├── code-review/
        ├── debugging/
        └── architecture/


A regra será:

Uma skill deve existir no nível mais baixo possível que ainda permita sua reutilização.

12. Session Handoff

A continuidade entre sessões será responsabilidade do ai-memory e das skills de handoff.

O objetivo é permitir:

Sessão A
   ↓
trabalho
   ↓
decisões
   ↓
estado atual
   ↓
handoff
   ↓
Sessão B
   ↓
continuação


Não devemos depender de copiar manualmente o histórico da conversa.

O ai-memory foi projetado justamente para permitir que um agente seja interrompido e outro agente continue o trabalho utilizando a memória compartilhada.

13. Memória compartilhada

A memória terá diferentes níveis conceituais.

MEMORY
│
├── Global
│   └── conhecimento comum
│
├── Project
│   └── conhecimento do projeto
│
├── Agent
│   └── conhecimento específico do agente
│
└── Session
    └── contexto episódico


Isso permite que:

Developer
    │
    └── aprende algo
             │
             ▼
         ai-memory
             │
       ┌─────┴─────┐
       ▼           ▼
    CEO         Researcher


outros agentes possam recuperar o conhecimento quando necessário.

O ai-memory já possui uma convenção para páginas de decisão e recomenda registrar decisões duráveis de forma estruturada.

15. Conhecimento compartilhado

Nem tudo pertence a um agente.

Por exemplo:

Projeto
├── arquitetura
├── stack
├── regras de negócio
├── decisões
└── integrações


Esse conhecimento deve estar disponível para todos os agentes autorizados.

Enquanto:

Developer
├── técnicas de debugging
└── padrões de implementação


pode ser específico do agente.

16. Work

work/ será utilizado para artefatos temporários ou de trabalho.

Exemplo:

work/
├── research/
├── drafts/
├── experiments/
└── reports/


A regra será:

work/ contém artefatos de trabalho; ai-memory contém conhecimento que deve sobreviver ao trabalho.

Exemplo:

work/
└── análise-concorrente.md


Depois da análise, uma conclusão importante pode ser consolidada na memória.

17. Docs

docs/ contém documentação oficial do sistema.

Exemplo:

docs/
├── ARCHITECTURE.md
├── AGENTS.md
├── SKILLS.md
├── MEMORY.md
└── CONTRIBUTING.md


Esses arquivos não representam memória episódica.

São documentação estável do próprio sistema.

19. Fluxo de uma nova sessão

Quando uma nova sessão começa:

Session Start
     │
     ▼
AGENTS.md
     │
     ▼
Identidade do agente
     │
     ▼
ai-memory
     │
     ├── estado atual
     ├── decisões recentes
     ├── contexto relevante
     └── handoff anterior
     │
     ▼
Skill necessária
     │
     ▼
Execução


A memória não deve ser carregada integralmente.

O agente deve recuperar apenas aquilo que é relevante para a tarefa.

Esse princípio é importante porque o ai-memory utiliza uma camada de retrieval sobre a wiki, incluindo busca textual e relações entre páginas, mantendo o Markdown como fonte de verdade.

20. Fluxo de aprendizado

O sistema deverá evoluir continuamente.

Trabalho
   ↓
Observação
   ↓
Resultado
   ↓
Aprendizado
   ↓
ai-memory
   ↓
Próxima tarefa
   ↓
Melhor resultado


Quando um aprendizado se tornar uma regra permanente, ele deverá ser promovido para AGENTS.md.

Quando se tornar um procedimento reutilizável, deverá ser promovido para uma Skill.

Quando for apenas conhecimento contextual, permanecerá no ai-memory.

Assim:

Experiência
    │
    ├── regra permanente
    │       ↓
    │    AGENTS.md
    │
    ├── procedimento repetível
    │       ↓
    │     SKILL.md
    │
    └── conhecimento contextual
            ↓
         ai-memory

24. Ordem de implementação

A implementação será feita incrementalmente.

Fase 1 — Fundação

Criar:

agent-os/
├── AGENTS.md
├── agents/
├── skills/
├── memory/
├── work/
└── docs/


Criar o primeiro agente:

agents/ceo/
└── AGENTS.md


Objetivo:

ter um único agente funcionando corretamente antes de criar vários agentes.

Fase 2 — Integrar ai-memory

Instalar e configurar o ai-memory.

Configurar:

diretório de dados;
MCP;
hooks;
escopo do projeto;
persistência;
integração com o runtime escolhido.

Validar:

Sessão A
    ↓
trabalho
    ↓
Sessão encerrada
    ↓
Sessão B
    ↓
memória recuperada

Fase 3 — Skills

Criar as primeiras skills:

skills/
├── research/
├── documentation/
└── session-handoff/


Não criar dezenas de skills inicialmente.

Começar com poucas skills e observar quais procedimentos realmente se repetem.

Fase 4 — Segundo agente

Adicionar:

agents/developer/
└── AGENTS.md


Validar:

CEO
 │
 └── Developer
       │
       ├── Skills
       └── ai-memory

Fase 5 — Memória compartilhada

Validar se:

CEO
 │
 └── cria conhecimento
        │
        ▼
    ai-memory
        │
        ▼
   Developer


consegue recuperar corretamente o conhecimento.

Fase 6 — Handoff

Implementar o fluxo:

Agent A
   ↓
session
   ↓
handoff
   ↓
ai-memory
   ↓
Agent B


O objetivo é permitir que diferentes runtimes possam continuar o mesmo trabalho.

Fase 7 — Learning Loop

Depois que a arquitetura básica estiver estável:

sessões
   ↓
observações
   ↓
aprendizados
   ↓
ai-memory
   ↓
análise periódica
   ↓
novas skills
   ↓
melhores agentes


O ai-memory já possui mecanismos de consolidação e auto-improvement que podem servir como base para essa etapa.

26. Referência principal

A implementação da camada de memória deverá seguir a arquitetura oficial do projeto ai-memory, especialmente:

docs/design-decisions.md;

A parte mais importante é não tentar reproduzir dentro de memory/ o que o ai-memory já faz. O próprio projeto já separa wiki Markdown (fonte de verdade), banco SQLite (índice), sessões, observações e handoffs.
