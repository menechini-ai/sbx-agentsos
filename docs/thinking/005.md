2. Hierarquia de autoridade

Esse é um dos guardrails mais importantes.

Eu definiria:

L0 — GOVERNANCE
     ↓
L1 — CEO
     ↓
L2 — Department Agent
     ↓
L3 — Developer / Specialist Agent
     ↓
L4 — Subagent
     ↓
L5 — Tool / MCP


E a regra:

Nível inferior NÃO pode sobrescrever
uma regra de nível superior.


Por exemplo:

CEO
 └── Developer
      └── Code Reviewer
           └── Test Runner


O Test Runner pode retornar:

{
  "status": "failed",
  "reason": "3 tests failed"
}


Mas ele não pode decidir:

"Vou ignorar os testes porque acho que o código está correto."

3. Contrato INPUT entre agentes

Eu não deixaria agentes conversarem com texto completamente livre.

Use um envelope padrão.

task:
  id: TASK-2026-0001
  parent_id: TASK-2026-0000

sender:
  agent: ceo
  level: 1

receiver:
  agent: developer
  level: 2

objective:
  primary: "Implementar autenticação"

context:
  repository: "project"
  branch: "feature/auth"

constraints:
  - "Não alterar arquitetura global"
  - "Não adicionar dependências sem aprovação"
  - "Manter compatibilidade com API atual"

resources:
  skills:
    - authentication
    - testing

  tools:
    - github
    - filesystem

memory:
  read:
    - "decisions/authentication.md"

expected_output:
  type: implementation_report
  required:
    - status
    - changes
    - tests
    - risks

deadline:
  priority: high


Assim o agente sabe:

quem pediu;
para quem;
qual é a missão;
qual o contexto;
quais são os limites;
quais skills pode usar;
quais memórias pode consultar;
qual output deve produzir.
4. Contrato OUTPUT

Todo agente deve devolver um output estruturado.

result:
  task_id: TASK-2026-0001

  status: completed

  summary:
    - "Autenticação implementada"
    - "Testes adicionados"

  changes:
    files:
      - src/auth/login.ts
      - tests/auth/login.test.ts

  validation:
    tests:
      status: passed
      total: 42

  risks:
    - "JWT expiration ainda usa configuração padrão"

  assumptions:
    - "API existente deve permanecer compatível"

  memory_candidates:
    - type: learning
      description: "Projeto utiliza refresh token de 7 dias"

  improvement_candidates:
    - type: skill
      name: "auth-testing"
      reason: "Padrão repetido em 4 tarefas"

  handoff:
    next_agent: qa
    required: true


Isso cria uma cadeia verificável:

INPUT
  ↓
PROCESSAMENTO
  ↓
VALIDAÇÃO
  ↓
OUTPUT
  ↓
HANDOFF

5. Guardrails

Eu dividiria os guardrails em quatro categorias.

Guardrail 1 — Authority

Define o que o agente pode decidir.

Exemplo:

authority:
  can:
    - read_repository
    - modify_assigned_files
    - run_tests

  cannot:
    - change_governance
    - create_root_agent
    - modify_security_policy
    - delete_memory

Guardrail 2 — Scope

Define onde ele pode trabalhar.

scope:
  allowed_paths:
    - src/
    - tests/

  denied_paths:
    - governance/
    - production/
    - secrets/

Guardrail 3 — Tool

Define quais ferramentas podem ser usadas.

tools:
  allowed:
    - github.read
    - github.write
    - filesystem.read
    - filesystem.write

  denied:
    - production.deploy
    - secrets.export

Guardrail 4 — Change

Define o que pode ser alterado automaticamente.

LOW RISK
  código
  testes
  documentação
  exemplos

MEDIUM RISK
  dependências
  configuração
  skills

HIGH RISK
  AGENTS.md
  GOVERNANCE.md
  guardrails
  MCP permissions
  memória permanente
  criação de agents


E eu colocaria:

LOW       → automático
MEDIUM    → revisão do Agent superior
HIGH      → aprovação CEO/humano

6. Regra fundamental: trabalhar primeiro, melhorar depois

Essa é uma melhoria importante na arquitetura.

Não queremos:

recebe tarefa
   ↓
"vou criar uma nova skill"
   ↓
"vou criar um novo agent"
   ↓
"vou modificar a arquitetura"
   ↓
nunca termina a tarefa


Queremos:

TAREFA
  ↓
EXECUTAR
  ↓
VALIDAR
  ↓
ENTREGAR
  ↓
ANALISAR
  ↓
APRENDER
  ↓
PROPOR MELHORIA


Portanto:

Improvement MUST NOT block execution unless the existing system is incapable of safely completing the task.

7. Ciclo de aprendizagem

Depois de concluir uma tarefa, o agente entra em:

POST-TASK REVIEW


Ele responde:

review:
  task_id: TASK-2026-0001

  what_worked:
    - "Skill X resolveu 80% da tarefa"

  what_failed:
    - "Não havia skill para testes de integração"

  repeated_pattern:
    detected: true
    occurrences: 5

  improvement:
    type: new_skill
    proposal: "integration-testing"

  confidence:
    score: 0.87


Isso vai para:

memory/candidates/


e não diretamente para a memória oficial.

8. Memória → Skill

Eu colocaria uma política explícita.

Uma memória pode virar Skill quando:

mesmo conhecimento
        +
repetição
        +
resultado comprovado
        +
procedimento generalizável


Por exemplo:

TASK 1
"Como testar API?"

TASK 2
"Como testar API?"

TASK 3
"Como testar API?"

TASK 4
"Como testar API?"


O sistema percebe:

PATTERN DETECTED


E propõe:

skills/api-testing/SKILL.md


Mas não cria automaticamente.

Fluxo:

memory
  ↓
candidate
  ↓
pattern detection
  ↓
proposal
  ↓
review
  ↓
skill

9. Memória → Regra

Aqui o nível de exigência deve ser maior.

Uma regra não deveria nascer simplesmente porque um agente achou uma boa ideia.

Por exemplo:

Memory:

"Durante três tarefas tivemos problemas quando
agentes modificaram dependências sem avisar."


Pode gerar:

RULE CANDIDATE:

Agents MUST NOT add dependencies
without declaring the dependency change.


Fluxo:

memory
  ↓
repeated failure
  ↓
rule candidate
  ↓
impact analysis
  ↓
approval
  ↓
governance rule

10. Memória → novo Agent

Também deve exigir evidência.

Por exemplo:

20 tarefas
     ↓
mesmo domínio
     ↓
mesmas ferramentas
     ↓
mesmo tipo de decisão
     ↓
alto volume


Então:

Candidate Agent:

database-specialist


O sistema pode propor:

proposal:
  type: new_agent

  name: database-specialist

  reason:
    - "17 tasks related to database optimization"
    - "Existing developer agent overloaded"

  responsibilities:
    - query optimization
    - schema review
    - migration analysis

  required_skills:
    - sql
    - database-performance

  required_tools:
    - database

17. Regra de ouro para autoaperfeiçoamento

Eu colocaria literalmente no GOVERNANCE.md:

SELF-IMPROVEMENT POLICY

Agents are encouraged to identify weaknesses,
missing capabilities, repeated patterns and
opportunities for improvement.

Agents MUST prioritize completing the assigned
task before performing optimization work.

Agents MUST NOT modify governance, permissions,
guardrails, hierarchy or authority autonomously.

Agents MAY propose:

- new skills
- skill improvements
- new agents
- agent improvements
- workflow improvements
- documentation improvements
- memory promotion
- rule candidates

Proposals MUST be reviewed according to their
risk level before becoming active system components.

18. Matriz de autorização

Essa tabela ajuda muito:

Ação	Subagent	Agent	CEO
Ler memória	✅	✅	✅
Criar memória candidata	✅	✅	✅
Alterar código da tarefa	✅	✅	✅
Criar Skill proposal	✅	✅	✅
Ativar Skill	❌	⚠️	✅
Criar Agent proposal	❌	✅	✅
Ativar Agent	❌	❌	✅
Alterar Guardrail	❌	❌	✅
Alterar Governance	❌	❌	🔐
Alterar hierarquia	❌	❌	🔐
Alterar MCP permissions	❌	⚠️	✅

⚠️ = pode propor/solicitar, mas não efetivar.

🔐 = mudança excepcional, idealmente com aprovação humana.

19. O princípio que fecha a arquitetura

Eu adicionaria um conceito chamado Capability Lifecycle:

OBSERVE
   ↓
LEARN
   ↓
REUSE
   ↓
IDENTIFY GAP
   ↓
PROPOSE
   ↓
REVIEW
   ↓
TEST
   ↓
APPROVE
   ↓
DEPLOY
   ↓
MONITOR
   ↓

Então o sistema não funciona assim:

Agent → cria coisas aleatoriamente


Ele funciona assim:

                ┌───────────────┐
                │    EXECUTE    │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │    LEARN      │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │    PROPOSE    │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │    REVIEW     │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │     TEST      │
                └───────┬───────┘
                        ↓
                ┌───────────────┐
                │    APPROVE    │
                └───────┬───────┘

Essa seria minha recomendação final: primeiro implementar contratos INPUT/OUTPUT + hierarquia + guardrails + handoff. Depois conectar o memory/knowledge.
