Sim. Para essa arquitetura, eu criaria guardrails + contratos de I/O como uma camada independente da lógica dos agentes. A ideia é que CEO → Agent → Subagent tenha um protocolo previsível, sem permitir que um agente “pule” a hierarquia.

1. Princípio da arquitetura

A comunicação deve seguir:

                    ┌─────────────────┐
                    │       CEO       │
                    │ Orchestrator    │
                    └────────┬────────┘
                             │
                    Delegation Contract
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
      ┌───────────────┐             ┌───────────────┐
      │    Agent A    │             │    Agent B    │
      │   Developer   │             │   Research    │
      └───────┬───────┘             └───────────────┘
              │
       Subagent Contract
              │
       ┌──────┴──────┐
       ▼             ▼
  ┌─────────┐   ┌─────────┐
  │Subagent │   │Subagent │
  │   Test  │   │ Review  │
  └─────────┘   └─────────┘


A regra principal:

Um agente só pode delegar para seus filhos autorizados e só pode retornar para seu pai.

Assim você evita:

CEO → Subagent
Developer → CEO diretamente
Subagent → outro Agent
Subagent → Subagent de outra área


a menos que exista uma regra explícita de escalonamento.

3. O contrato de entrada

Todo trabalho delegado deveria possuir uma estrutura mínima.

Por exemplo:

task:
  id: "TASK-2026-000123"

  parent:
    agent: "ceo"

  target:
    agent: "developer"

  type: "implementation"

  objective: >
    Implementar o sistema de memória utilizando memory/knowledge.

  context:
    repository: "project-x"
    branch: "feature/memory/knowledge"

  constraints:
    - "Não alterar a arquitetura de agentes."
    - "Não modificar o contrato de memória."
    - "Seguir os padrões existentes."

  inputs:
    files:
      - "memory/"
      - "agents/developer/"

  expected_output:
    type: "implementation_report"

  acceptance_criteria:
    - "Código implementado."
    - "Testes executados."
    - "Documentação atualizada."

  permissions:
    filesystem:
      read: true
      write: true

    git:
      read: true
      write: true
      commit: false

    delegation:
      allowed: true
      children:
        - "developer.test"
        - "developer.reviewer"

  deadline: null


Esse contrato é importante porque o Developer não recebe simplesmente:

"Faça isso."


Ele recebe uma unidade de trabalho formalizada.

4. Guardrail de entrada

Crie:

contracts/guardrails/input.md


Com regras como:

# Input Guardrails

Todo agente deve validar o input antes de executar uma tarefa.

## Obrigatório

O input deve possuir:

- task.id
- parent.agent
- target.agent
- task.type
- task.objective
- task.constraints
- task.expected_output
- task.acceptance_criteria
- permissions

## Rejeitar quando

O agente deve rejeitar a tarefa quando:

1. target.agent não corresponde ao próprio agente.
2. parent.agent não é um agente autorizado.
3. a tarefa viola a hierarquia.
4. permissions não permitem a operação solicitada.
5. faltam critérios de aceite.
6. o objetivo é ambíguo demais para execução segura.
7. a tarefa exige uma ferramenta não autorizada.

## Não assumir

O agente não deve inferir:

- permissões;
- autoridade;
- escopo;
- requisitos críticos;
- aprovação;
- capacidade de delegação.


A última regra é especialmente importante.

Ausência de permissão não significa permissão.

5. Contrato de saída

O agente nunca deveria retornar apenas:

"Pronto."


Use:

result:

  status: "completed"

  agent:
    id: "developer"

  summary: >
    Implementada integração inicial com memory/knowledge.

  outputs:
    files_changed:
      - "memory/memory/knowledge/config.yaml"

  validation:

      status: "passed"

    - criterion: "Testes executados"
      status: "passed"

    []

  recommendations:

8. Guardrail de hierarquia

Esse é provavelmente o guardrail mais importante.

Crie:

contracts/guardrails/hierarchy.md


Por exemplo:

# Hierarchy Guardrails

## Hierarchy

CEO
├── Developer
│   ├── Developer.Test
│   └── Developer.Reviewer
│
├── Research
│   ├── Research.Search
│   └── Research.Analyst
│
└── Operations

## Rules

1. Um agente só recebe tarefas do seu parent autorizado.

2. Um agente só pode delegar para children autorizados.

3. Um subagent não pode delegar para seu uncle.

4. Um subagent não pode delegar para o CEO diretamente.

5. Escalonamentos devem retornar primeiro ao parent.

6. O CEO é o único agente com autoridade global.

7. Nenhum agente pode aumentar suas próprias permissions.

8. Um agente não pode alterar seu próprio AGENTS.md.

9. Um agente não pode alterar seus próprios guardrails.

10. Delegação deve sempre criar um novo task.id.

11. O parent continua responsável pelo resultado final da tarefa delegada.


A regra 11 é fundamental.

Se:

CEO
 ↓
Developer
 ↓
Developer.Test


o Developer.Test não responde diretamente pela missão do CEO.

A cadeia de responsabilidade continua:

CEO
 ↓
Developer
 ↓
Developer.Test
 ↓
Developer
 ↓
CEO

9. Delegação deve criar contexto filho

Nunca faça:

parent_task: TASK-001
child_task: TASK-001


Faça:

TASK-001
│
└── TASK-001.01


Exemplo:

task:
  id: "TASK-001.01"

  parent_task:
    id: "TASK-001"

  parent_agent: "developer"

  target_agent: "developer.test"

  objective: >
    Validar a integração do memory/knowledge.

  scope:
    - "executar testes"
    - "identificar falhas"

  permissions:
    filesystem:
      read: true
      write: false

    git:
      read: true
      write: false

    delegation:
      allowed: false


Assim o subagent recebe somente o contexto necessário.

10. Princípio de mínimo privilégio

Cada nível deve possuir permissões diferentes.

Exemplo:

Capacidade	CEO	Agent	Subagent
Ler projeto	✅	✅	✅
Escrever código	✅	✅	conforme tarefa
Criar Agent	✅	❌	❌
Alterar AGENTS.md	⚠️	❌	❌
Alterar guardrails	⚠️	❌	❌
Delegar	✅	limitado	geralmente ❌
Escalar	✅	✅	para parent
Alterar memória	✅	limitado	conforme tarefa
Promover memória	✅	propor	❌
Alterar MCP	✅	conforme autorização	❌

Eu separaria propor de aprovar.

12. Guardrail de memória

Uma regra que eu colocaria:

# Memory Guardrails

Agents MUST NOT treat every observation as durable memory.

Memory can be:

- temporary
- episodic
- semantic
- procedural
- candidate

Only approved memories can become durable organizational knowledge.

Agents may propose memory promotion.

Agents cannot unilaterally promote memory into:

- AGENTS.md
- SKILL.md
- global rules
- security policies
- hierarchy rules


Isso evita um problema sério:

um agente descobrir algo uma vez e transformar aquilo em regra permanente.

14. Memória → Regra

Aqui eu colocaria um nível ainda mais alto de proteção.

memory
   ↓
candidate
   ↓
evidence
   ↓
review
   ↓
proposal
   ↓
CEO approval
   ↓
AGENTS.md / policy


Ou seja:

MEMORY → SKILL


pode ser relativamente frequente.

Mas:

MEMORY → RULE


deve ser raro.

Uma regra poderia exigir:

promotion:
  target: "rule"

  requirements:
    min_occurrences: 5
    min_success_rate: 0.90
    human_or_ceo_approval: true
    security_review: false


Para regras de segurança, hierarquia ou permissões:

security_sensitive: true
approval:
  required: true
  authority: "ceo"

17. Guardrail global

No AGENTS.md raiz eu colocaria algo como:

# Global Agent Policy

## Authority

The CEO is the root orchestrator.

Agents operate only within their assigned scope.

## Hierarchy

Agents MUST respect parent-child relationships.

## Delegation

Delegation MUST:

1. target an authorized child;
2. create a new task ID;
3. define explicit scope;
4. define permissions;
5. define expected output;
6. preserve the parent task reference.

## Input

Agents MUST validate every incoming task.

## Output

Agents MUST return structured results.

## Memory

Agents MUST distinguish temporary knowledge from durable knowledge.

## Promotion

Memory MUST NOT automatically modify:

- AGENTS.md
- SKILL.md
- global policies
- hierarchy
- security rules

## Safety

When authority or scope is ambiguous:

STOP and escalate to the parent.

## Integrity

Agents MUST NOT:

- modify their own authority;
- bypass their parent;
- create unauthorized agents;
- alter guardrails to complete a task;
- hide failures;
- report success without validation.

20. A regra de ouro

Eu resumiria a arquitetura em 6 invariantes:

1. IDENTIDADE
   Quem sou?

2. HIERARQUIA
   Quem é meu pai?
   Quem são meus filhos?

3. AUTORIDADE
   O que posso fazer?

4. CONTRATO
   O que recebi?
   O que preciso devolver?

5. MEMÓRIA
   O que devo lembrar?
   O que pode virar conhecimento permanente?

6. HANDOFF
   Para quem devo devolver o resultado?


E o guardrail mais importante:

Nenhum agente pode usar uma capacidade simplesmente porque tecnicamente consegue usá-la. Ele só pode utilizá-la se o contrato, a hierarquia e suas permissões autorizarem.

Isso deixa sua arquitetura preparada para crescer de:

CEO
 └── Developer


para algo como:

CEO
├── Product
│   ├── Research
│   └── Analyst
│
├── Developer
│   ├── Backend
│   ├── Frontend
│   ├── Test
│   └── Reviewer
│
├── DevOps
│   ├── CI
│   └── Infrastructure
│
└── Security
    ├── Audit
    └── Reviewer


sem perder o controle da comunicação.

Eu faria essa camada de contratos antes de integrar o memory/knowledge de forma definitiva, porque o memory deve armazenar não só conteúdo, mas também proveniência, task_id, agente que criou a informação, nível de confiança e histórico de promoção. Isso permitirá posteriormente auditar exatamente “qual agente aprendeu isso, em qual tarefa e por que isso virou uma skill/regra”.
