53. Agent

O Agent é uma definição, não uma execução.

interface Agent {
  id: string
  name: string
  version: string

  level: AgentLevel
  role: string

  parent?: string

  capabilities: string[]

  model: ModelConfig

  policies: string[]

  skills: string[]

  status: "active" | "disabled" | "deprecated"
}


Exemplo:

name: Developer

level: L2

parent: agent.ceo

capabilities:
  - repo.read
  - repo.write
  - git.commit
  - github.pull_request.create

skills:
  - coding
  - testing
  - debugging


Observe que:

Agent não contém segredo, token ou acesso físico.

Ele apenas declara o que potencialmente pode fazer.

54. AgentInstance

interface AgentInstance {

"faça X"

57. Capability

Aqui está uma das partes mais importantes.

interface Capability {
  id: string

  action: string
  resource: ResourceSelector

  constraints: CapabilityConstraint[]

  delegatable: boolean

  expires_at?: string
}


Exemplo:

    allowed:
      - .ts
      - .js
      - .json

  - type: max_size
    value: 1000000

delegatable: true


Agora podemos fazer autorização extremamente granular.

58. Capability Grant

O Agent Registry define capacidades.

Mas uma execução recebe grants temporários.

interface CapabilityGrant {
  capability_id: string

  granted_to: string

  granted_by: string

  scope: unknown

  issued_at: string

  expires_at?: string

  delegation_chain: string[]
}


Isso permite rastrear:

 ↓

 ↓

59. Regra de delegação

Eu colocaria uma invariável no kernel:

child capabilities ⊆ parent capabilities


Nunca:

child capabilities > parent capabilities


Exemplo:

Developer
├── repo.read
├── repo.write
└── git.commit


pode criar:

Test Runner
├── repo.read
└── test.execute


mas não:

Test Runner
└── production.deploy


se o Developer não possui essa capacidade.

60. Policy

A Policy decide se uma operação é permitida.

interface Policy {
  id: string

  subject: SubjectSelector

  action: ActionSelector

  resource: ResourceSelector

  effect: "allow" | "deny" | "approval_required"

  conditions?: Condition[]
}


Exemplo:

id: policy.production.deploy

subject:
  level: L2

action:
  equals: production.deploy

effect: approval_required

61. Policy Engine

A API poderia ser:

interface PolicyEngine {
  authorize(
    actor: Actor,
    action: Action,
    resource: Resource,
    context: PolicyContext
  ): AuthorizationDecision
}


Resultado:

interface AuthorizationDecision {
  effect: "allow" | "deny" | "approval_required"

  reason: string

  matched_policies: string[]

  risk: RiskScore
}


Assim o runtime não precisa saber como a política funciona.

Ele simplesmente pergunta:

"Posso?"

62. Não permitir allow implícito

Eu usaria uma regra:

default deny.

Se não existir uma política permitindo:

DENY


Isso é muito mais seguro.

Policy found?
 ├── yes → evaluate
 └── no  → DENY


Especialmente para ferramentas novas.

63. Ordem das políticas

Também precisamos definir precedência.

Eu usaria:

Explicit DENY
      ↓
Critical governance
      ↓
Approval requirement
      ↓
Explicit ALLOW
      ↓
Default DENY


Portanto:

DENY > APPROVAL > ALLOW


Isso evita que uma regra genérica permita algo proibido por uma regra específica.

64. Risk Engine

Separaria Risk de Policy.

interface RiskEngine {
  evaluate(
    actor: Actor,
    action: Action,
    resource: Resource,
    context: RiskContext
  ): RiskAssessment
}


Resultado:

{
  "score": 8.4,
  "level": "high",
  "factors": [
    "production",
    "write",
    "external_system"
  ],
  "requires_approval": true
}


Assim podemos mudar a política de risco sem reescrever o agente.

65. Approval

Approval deveria ser uma entidade persistente.

interface Approval {
  id: string

  requested_by: string

    | "approved"
    | "rejected"
    | "expired"

  created_at: string

Isso é muito melhor que:

perdido no histórico do chat.

66. Execution

interface Execution {
  id: string

    | "pending"
    | "running"
    | "completed"
    | "failed"

  finished_at?: string

Por exemplo:

 ├── execution #3 → file.write
 ├── execution #4 → test.run
 └── execution #5 → git.commit


Agora temos uma trilha completa.

98. A métrica mais importante

Eu criaria uma métrica chamada:

Unauthorized Action Rate
unauthorized_attempts
──────────────────────
total_action_attempts


O objetivo:

0%


Não porque agentes nunca tentem algo errado.

O objetivo é:

agentes podem raciocinar errado, mas não podem executar ações não autorizadas.

Essa é uma diferença enorme.
